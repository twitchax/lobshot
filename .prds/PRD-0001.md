# Summary
The M0 scaffold: the workspace from `DESIGN.md` ("Architecture"), the gate green, the image
building, and the server serving an empty Bevy canvas through trunk. No game yet.

# Problem
Every later milestone needs the five crates, a wasm build that works end to end, and a server that
serves it, before any rules or rendering can land.

# Goals
1. `cargo make ci` is green, including the wasm32 lint.
2. `cargo make dev` serves a Bevy canvas at http://127.0.0.1:8080 and at `/r/<code>`.
3. `docker build` produces an image that serves the same.

# Technical Approach
- `bootstrap-rust-project workspace --docker --xtask`, reshaped: the generated library became
  `lobshot-sim` (keeping `base`), the CLI crate became `lobshot-lab`, `lobshot-server` was ported
  from the `service` template (`config`, `server`, the HTTP and e2e tests), and `lobshot-client`
  is new.
- The server routes `/healthz`, `/r/{code}` (the page) and the bundle through `tower-http`'s
  `ServeDir`, with precompressed siblings and `Cache-Control: no-cache`.
- `cargo xtask dist` runs trunk with the `wasm-release` profile (opt-level `s`) and wasm-opt `s`,
  then writes `.br` (quality 11, 16 MiB window) and `.gz` siblings and prints sizes.

# Assumptions
- trunk downloads the matching wasm-bindgen and wasm-opt itself; nothing installs them globally.

# Constraints
- The client builds only for wasm32: native tasks exclude it.

# References to Code
- `crates/server/src/server.rs`, `crates/client/src/main.rs`, `xtask/src/dist.rs`, `Dockerfile`,
  `Makefile.toml`.

# Non-Goals (MVP)
- Game rules, rendering, networking: M1 and M2.
- The release workflow: the generated one zipped a bare binary with no client bundle, so it was
  removed; self-hosting is the image.
